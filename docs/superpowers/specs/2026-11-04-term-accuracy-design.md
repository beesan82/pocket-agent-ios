# 専門用語の誤認識対策（代替候補の選び直し／用語辞書）

## 目的

精度改善サイクルの手順 2。固定文 C（会議・専門用語、新系列 CER 8.64%）の誤りは専門用語に集中している：

| 正解 | 認識結果 |
|---|---|
| 露光装置 | 路行装置 |
| 歩留まり | ぶどまり |
| 線幅 | 先幅 |
| 規格 | 企画 |

エンジン側に用語を教える手段が無い（下記「前提」）ため、エンジンが出した情報の範囲で直す手を 2 つ、効果を測りながら順に試す。どちらも固定文 A〜C の物差し（新系列、ADR-046）は変えず、対策の ON/OFF 比較で効果だけを見る。

## 前提（確定済みの制約）

- 主経路のエンジンは `SpeechAnalyzer` + `SpeechTranscriber`（長文用）。このモジュールには用語ヒント（contextual strings）やカスタム語彙の公式手段が無い（Apple エンジニアのフォーラム発言ほか複数ソースで確認済み）。
- 用語ヒントがあるのは短文用の `DictationTranscriber` だけで、会議等の長文が主用途の本アプリの主経路には採用しない。
- 採点とログの規則は既存どおり：`TranscriptionCheck.evaluate` で採点し、測定ログには件数と CER のみ残す（本文・音声は残さない、ADR-026）。自動チェックは合成音声の物差しであり、エンジン設定は日誌のライブ経路と同一に保つ（ADR-044）。

## コード調査の結果（2026-11-04、main 0bbe3b5 時点）

### 現在の設定と結果の消費

- 単言語経路（日誌・音声入力・自動チェック）は `SpeechTranscriber(locale:preset:)` の `.progressiveTranscription` preset（`SpeechCapture.swift` の `AudioPipeline.make`、`TranscriptionAutoChecker.swift`）。二言語経路だけが明示オプションで、`reportingOptions: [.volatileResults, .fastResults]`、`attributeOptions: [.audioTimeRange, .transcriptionConfidence]`。
- 結果の消費は `result.text`（`String(result.text.characters)` へ平坦化）、`result.isFinal`、`result.range` のみ。confidence 属性は二言語経路の `report(_:text:language:)` だけが run 単位で読み、`ConfidenceMath.weightedAverage` で言語判定（`LanguageArbiter`）に使う。単言語経路は confidence を読まない。
- **代替候補（alternatives）は現在の設定では取得できていない。** コード全体（App / Packages）に `alternatives` への参照は無い。

### 代替候補の有効化方法と副作用

- 代替候補は `SpeechTranscriber.Result.alternatives: [AttributedString]`（尤度順）に返る。有効化は **reportingOptions へ `.alternativeTranscriptions` を追加**する（attributeOptions ではない。属性は `.audioTimeRange` と `.transcriptionConfidence` の 2 つだけ）。
- preset の構成上、`.transcriptionWithAlternatives` は volatile results と fast results を含まない。ライブ表示（volatile）に依存する単言語経路では preset の単純な差し替えはできない。正しい変更は、`.progressiveTranscription` のオプション集合を取り出し、reportingOptions に `.alternativeTranscriptions` を union して、フルイニシャライザ `SpeechTranscriber(locale:transcriptionOptions:reportingOptions:attributeOptions:)` で組み立てること。preset は合成可能で、各オプション集合の getter と合成用イニシャライザが公開されている。
- 副作用・注意：
  - 選び直しは final 結果にだけ適用する（volatile は表示専用で、従来どおり素通し）。
  - 代替候補 1 件あたりの件数上限や処理コスト（メモリ・時間）は未計測。自動チェックで ON/OFF の所要時間を実機で比べる。
  - 候補ごとの信頼度は公開されていない（alternatives は文字列の配列のみ）。採用条件は信頼度ではなく「用語の含有」で設計する。
  - 言語資産の追加ダウンロードは不要のはずだが、未確認（実装時に CI と実機で確認する）。

### 粒度

- 代替候補は **Result 単位**。1 つの final Result がカバーする音声区間（現在の結合単位＝文節〜文程度のチャンク）の全文に対する代替解釈が配列で返る。run（単語）単位の差し替え候補ではない。
- したがって選び直しは「final Result ごとに、候補集合 `[text] + alternatives` の中から 1 つを選ぶ」が基本形になる。

### 自動チェック側

- `TranscriptionAutoChecker` は同一 preset・同一の Result 型を消費し、final の `text` だけを結合して返す。オプションを揃えれば同じ形状（alternatives 付きの Result）が得られるので、実験は自動チェックで回せる。
- ただし現行の戻り値は文字列のみ。実験では alternatives を含む結果を返す拡張が要る。
- 不変条件（ADR-044）との関係：自動チェックの**標準設定**はライブ経路と同一に保つ。実験は検証画面の明示的な ON/OFF 切り替えとして分離し、同一ビルド・同一音源で ON/OFF を比較できるようにする。実験 1 を採用する場合は、ライブ経路と自動チェックの両方の設定を対で変える。

## 実験 1：代替候補の選び直し

### 用語リスト

- 置き場所：`PocketAgentCore`（純ロジックとして CI でテストできる場所。採点器 `TranscriptionScorer` と同じ層）。
- 形式：正規用語の配列を持つ型（案：`TranscriptionTerms`）。初期セットは半導体ドメインの語から作る。対象 4 語（露光装置、歩留まり、線幅、規格）を必ず含み、周辺語（半導体、ウェハ、洗浄、成膜、エッチング、イオン注入、ダイシング、ボンディング、検査、納期、測定）も足す。実験段階では固定リストとし、ユーザー編集可能な辞書への拡張は製品化の判断に回す。

### 候補の評価と採用条件

純ロジック（案：Core の `AlternativeSelector`）として実装し、App 側は Result から候補文字列を取り出して渡すだけにする。

- 候補集合：`[result.text] + result.alternatives`（いずれも採点と同じ正規化をかけた文字列で比較する）。
- 評価：各候補について (a) 用語リストの語の出現数、(b) 元の `text` との編集距離（文字数差の目安でよい）を数える。
- 採用条件：用語出現数が元の `text` より多い候補がある場合に限り、その中で編集距離が最小のものを採用する。同点（用語数が同じ）なら元の `text` を維持し、無用な差し替えをしない。

### 測定方法

- 自動チェックに実験 ON/OFF を付け、C を両条件で測る。A・B も両条件で測り、退行が無いかを見る。
- 指標は評価プロトコル（後述）の C の CER と用語エラー数。加えて、代替候補の中に対象用語が何回現れたか（候補の「当たり率」）を画面表示で記録する。本文はログに残さない。

## 実験 2：用語辞書による後処理

実験 1 で届かなかった誤りを、既知の誤認識ペアで決め打ち補正する。最終手段として位置づける。

### 登録形式

- 置き場所と形式：Core に誤→正のペア表（案：`TermCorrector`）。初期ペアは観測済みの誤りから作るが、安全度で 2 段に分ける：
  - **無条件ペア**：誤り文字列が通常の日本語として成立しないもの。例：路行装置→露光装置、ぶどまり→歩留まり。
  - **文脈条件ペア**：誤り文字列が通常語でもあるもの。例：企画→規格、先幅→線幅。単独では補正せず、前後の語などの文脈条件を満たすときだけ補正する（条件の具体化は実装計画で詰める。詰め切れないペアは登録しない）。

### 過剰補正を防ぐ条件

- 補正は final テキストにだけ適用する（volatile には適用しない）。
- 文脈条件ペアは、条件を満たさない出現を 1 件でも含む場合はそのペア自体を不採用にできるよう、ペア単位で ON/OFF できる形にする。
- A・B の自動チェック結果に補正が発動したら、その時点で過剰補正とみなして該当ペアを見直す（A・B は専門用語を含まないため、発動自体が異常信号）。

### 記録方法

- ADR-026 の流儀で、測定ログには**補正の適用件数のみ**を残す（対象語や本文は残さない）。自動チェックでは画面に件数を出し、CER 比較に使う。ログ行の形式は実装時にベースライン文書へ追記して定義する。

## 評価プロトコル

- 固定文 A〜C は凍結したまま変更しない。採点は新系列（ADR-046）で行う。
- 主指標：**C の CER**（現状 8.64%）と **C の用語エラー数**。用語エラー数の定義：正解文に含まれる対象用語（露光装置、歩留まり、線幅、規格の 4 語）のうち、認識文に正しく現れなかった個数。現状は 4 語とも誤りで **用語エラー数 = 4**。
- 退行検出：A・B の CER が対策 OFF の値（A 2.44%、B 0.00%）から悪化したら、その対策は不採用。
- 追加の専門用語文を作る場合：固定文セットには混ぜない。実験用の別枠（例：実験用 E1〜E3）として自動チェックの実験モード内だけで使い、A〜C の系列（物差し）を汚さない。
- 合成音声での効果確認が済んだら、最終判断の前に手動チェック（実声）でも C を 1 回測り、実声で退行が無いことを確認する。

## 実施順序と判断基準

順序は **実験 1 → 実験 2**。実験 1 はエンジン自身の情報を使う正攻法で、効く範囲が分かれば辞書で守る範囲を最小化できるため。

### 実験 1 の判断基準

- **採用**：C の用語エラー数が 4 → 2 以下、かつ C の CER が 8.64% から改善（目安 5% 以下）、A・B に退行なし。
- **不発として記録し実験 2 へ**：代替候補の中に対象用語が 1 件も現れない場合（エンジンが正解を候補にも持っていない）。
- **不採用**：上記の中間で、CER が改善しない、または A・B に退行が出る場合。

### 実験 2 の判断基準

- **採用**：C の用語エラー数が 4 → 1 以下、かつ C の CER が 5% 以下、A・B に退行なし（補正の発動ゼロを含む）。
- **不採用**：文脈条件ペアで過剰補正が抑えられない場合。その場合は無条件ペアだけの縮小採用もありうる（判断は測定結果を見て行う）。

### 両方とも不採用の場合

次の手（短文経路 `DictationTranscriber` の併用可否、認識後のオンデバイスモデルによる整文・補正）は、この物差しで測れる形に切り分けて別途設計する。ここでは結論を急がない。

## ADR 起票案（decisions.md へはまだ入れない）

**ADR-047（案）専門用語対策は代替候補の選び直し→用語辞書の順で実験する**

- 決定：固定文 C の専門用語エラー（新系列 CER 8.64%、用語エラー数 4）への対策として、まず `SpeechTranscriber` の代替候補（reportingOptions `.alternativeTranscriptions`）を用語リストで選び直す実験を行い、届かない範囲を用語辞書の後処理で補う実験を続ける。判断基準は設計書の数値どおりとする。
- 理由：主経路の `SpeechTranscriber` には用語ヒントの公式手段が無く、エンジンが出す情報の範囲で改善するしかない。代替候補はエンジン自身の再解釈であり、決め打ち補正より過剰補正の危険が小さい。
- 影響要件：なし（実験は検証画面の自動チェックから開始し、採用が決まるまでライブ経路の確定テキストは変えない）。

## 未確認事項

- `.progressiveTranscription` の正確なオプション構成（volatile / fast の有無）は SDK の実物で確認する。実装の最初のステップで、オプション集合をテストまたはログで確認してから組み立てる（リポジトリの決まり：SDK の使用例を推測で書かない）。
- 代替候補の最大件数、volatile 結果への付随の有無、ON/OFF の処理時間差は実機確認事項。
- 二言語経路への代替候補の適用は今回の実験の範囲外（言語判定 `LanguageArbiter` との相互作用を別途設計する）。
- 代替候補の採用が会議の実利用（長文・実声）でどう効くかは、自動チェックの合格後に手動チェックと会議モードで別途確認する。
