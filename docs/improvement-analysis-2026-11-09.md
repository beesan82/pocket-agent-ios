# 改善検討書（2026-11-09）— 文字起こし性能を軸に

対象: ポケット執事（開発名 Pocket Agent）。この文書は分析のみで、コード・ADR・チェックリストは変更していない。
前提（変更不可）: 存在理由は「金庫」（機微情報を端末内に閉じ込める、完全オンデバイス・オフライン）。現在の舵は文字起こしの性能改善で、きっかけは所有者の実使用での不満「文字起こし精度が悪い」。

表記: 【根拠】は読んだ文書・コードの位置、【推測】はコードや数値からの推定で、まだ検証していないもの。

---

## 1. 現状の到達点と残っている弱み

### 1.1 到達点（事実）

| 項目 | 状態 | 根拠 |
|---|---|---|
| 文字起こしエンジン | 日誌・会議とも Apple `SpeechAnalyzer` + `SpeechTranscriber`（`.progressiveTranscription` プリセット）で、端末内で動く | `App/PocketAgent/Speech/ProgressiveTranscriber.swift`、`SpeechCapture.swift` の `AudioPipeline.make` |
| 物差し | 固定文 A〜C を合成音声（VOICEVOX ずんだもん、16kHz）にしてアプリに同梱し、ファイルから直接認識して CER を出す自動チェック | ADR-044、`TranscriptionAutoChecker.swift` |
| 採点 | 漢数字と算用数字の正規化を入れた新系列。`tools/cer.py` と Core の `TranscriptionScorer` で同じルール | ADR-046 |
| 専門用語 | 代替候補の選び直し（実験 1）は効果なしで不採用。用語辞書 `TermCorrector`（4 ペア）は採用済み | ADR-047、ベースライン文書「実験1の測定」「実験2の測定と本採用」 |
| 適用範囲 | 単言語の確定テキスト（`SpeechCapture.consume`）と二言語経路の受理済み日本語セグメント（`MeetingSession.segmentText(for:)`）に辞書を常に適用 | ADR-047 follow-up、ADR-048 |
| 公式値 | 合成音声・辞書 ON で A 2.44% / B 0.00% / C 0.00%（辞書なしの C は 8.64%） | `docs/verification/2026-11-03-transcription-accuracy-baseline.md`「現在の公式値」 |

### 1.2 残っている弱み

#### W1（最大の弱み）: 実声での精度が一度も測られておらず、「改善した」と言える根拠が合成音声だけ
- 実声の記録表は全行が空欄で、本文には「実声のベースラインは 2026-11-04 時点で未実施」と書かれている。【根拠】ベースライン文書「記録表（実声）」
- チェックリストでも、実声の手動チェック、本採用後の実声での C の退行確認、実経路で辞書が発動するかの確認が、すべて未チェックのまま。【根拠】`docs/phase0-checklist.md` の「文字起こし精度チェックの自動化」「専門用語対策 実験2」の「実機で未検証」
- ADR-044 は、合成音声の CER を「回帰の物差しであり、実利用の精度そのものではない」と明記している。所有者の不満は実使用（実声・距離・雑音・複数話者）から出ているので、今の数字ではその不満が解消したかどうかを判断できない。
- 合成音声と実声の主な違い:
  - (a) 単一の合成話者で明瞭、雑音なし
  - (b) ファイルを一気に流し込む方式で、マイク・`AVAudioSession`・リアルタイム性を通らない（`TranscriptionAutoChecker.feed`）
  - (c) 距離 30cm・1m の条件がない
  - (d) 会議で起きる重なり発話・相槌・言い淀みがない
- 【推測】実声の CER は合成音声より大幅に悪い。特に会議（約 1m・机置き）が悪いはず。チェックリストには「会議の文字起こし精度が日誌より悪い件」が未解決の観察として残っている（「会議: ロック中の録音の修正」節）。

#### W2: C の 0.00% は「問題を見てから作った答え」の点数で、汎化を測っていない
- `TermCorrector.rules` の 4 ペアは、固定文 C の誤り 4 件そのものから作られている（コメント "Seeded from the errors observed in the fixed-passage C baseline"）。それを同じ C の同じ合成音声で採点して 0.00% になっている。【根拠】`Packages/PocketAgentCore/Sources/PocketAgentCore/TermCorrector.swift`、ADR-047
- 設計書は、追加の専門用語文を「実験用 E1〜E3」として別枠で持つ案を出していたが、まだ作られていない。【根拠】`docs/superpowers/specs/2026-11-04-term-accuracy-design.md`「評価プロトコル」
- A〜C は各 80 字前後（ref 81〜82 字）しかない。1 字の誤りで CER が約 1.2 ポイント動くので、差を見分ける力が粗い。【根拠】ベースライン文書の ref 文字数
- 過剰補正の懸念（【推測】、コードからの読み取り）: 「企画→規格」の発動条件には「を超え」が入っている。そのため「前回の企画を超える反響」のような普通の文も「規格」に書き換わる。現在のテストは「企画を立てる」系だけを守っている。【根拠】`TermCorrector.rules` の `spec`、ADR-047 の検証欄

#### W3: 辞書が固定で、所有者の実際の分野・語彙に合わせて育てる仕組みがない
- 辞書の中身は半導体の 4 語だけで、コードに直接書かれている。ユーザーが編集する経路はない。設計書には「ユーザー編集可能な辞書への拡張は製品化の判断に回す」とある。【根拠】`TermCorrector.swift`、`TranscriptionTerms.swift`、term-accuracy 設計書「用語リスト」
- 測定ログには件数と CER しか残さない方針（ADR-026）なので、所有者の実際の誤りは開発側に届かない。これは金庫の前提どおりで正しいが、誤り例を集める仕組みを端末の中に作らない限り、辞書は増えない。
- 所有者の実使用の分野が半導体かどうかは文書から分からない。【推測】固定文 C は例として選ばれた分野で、実際の誤りは別の語彙（人名・社内用語・製品名など）に集中している可能性が高い。

#### W4: 長時間会議で落ちた・止まったときに失うものが大きく、その様子を観測する手段もない
- 会議のセグメントはメモリ上の `segments` にしかなく、日誌への保存は「終了」時の `save()` 1 回だけ。日誌のテキスト入力には `JournalDraftStore` があるが、会議には途中保存がない。【根拠】`App/PocketAgent/Meeting/MeetingSession.swift`（`store.add` は `save()` の中にしかない）
- 【推測】ロック中の長い会議でメモリ不足によりアプリが強制終了されたり、クラッシュしたりすると、それまでの文字起こしがすべて消える。所有者から見れば「最悪の精度」と同じ体験になる。
- 「1 時間連続（メモリ・精度・発熱）」「1 時間の二言語会議」「録音中のモデル読み込みでメモリ警告が出ないか」は、すべて実機で未検証。【根拠】チェックリストの「会議モード」「二言語会議（段階 B）」節
- 会議中のメモリ・発熱・要点更新の所要秒を記録する測定ログの行がない。【根拠】`MeetingSession.swift` に測定ログへの書き込みがない。測定ログは `MLXValidationView` など検証画面が中心

#### W5: 録音側の条件（音声セッションのモード・距離）が検証されていない
- `AVAudioSession` は `.record` / `.measurement` で有効にしている。`.measurement` は端末側の音声処理を最小にするモードで、遠くの話者を拾う会議では不利かもしれない。チェックリストもこれを原因候補に挙げている。【根拠】`SpeechCapture.activateSession()`、チェックリスト「会議の文字起こし精度が日誌より悪い件」
- 自動チェックはマイクを通らないので、この設定の良し悪しを原理的に測れない（W1 の (b)）。

#### W6: 二言語経路は自動チェックの対象外
- 自動チェックは単言語・日本語だけ。二言語経路は SpeechTranscriber のオプションがプリセットと違い（`reportingOptions: [.volatileResults, .fastResults]` と `attributeOptions` を明示している）、言語判定（`LanguageArbiter`）も通る。この経路の精度・判定の正しさを再現性のある形で測る物差しがない。【根拠】`SpeechCapture.swift` の `AudioPipeline.make`、ADR-048（二言語ゲートは測定用として対象外）、チェックリスト「二言語ゲート（段階 A）」の未検証 4 件

#### W7: ダウンロードモデル格上げ（Qwen3-4B）のメモリ余裕の見込みが、記録上の数値と合わない
- ADR-042 は「測定 2 では 1.5B 読込後に `os_proc_available_memory` が 2972 MB 残っており」と書いている。しかし `docs/phase2-mlx-eval.md` では、2972 MB は**測定 1（Qwen3 1.7B、読込後 923 MB、途中でメモリ警告）**の値で、**測定 2（Qwen2.5 1.5B）の利用可能メモリは 2066 MB**になっている。
- 【推測】測定 2 を基準にすると、読み込み前の空きは約 2.9 GB（2066 + 831）。4B（読込後 2.5〜2.6 GB の見込み）では残りが数百 MB しかなく、ADR-042 の「1 GB 強の余裕」は楽観的すぎる。会議モードでは SpeechAnalyzer（二言語なら 2 系統）と翻訳も同時に動くので、さらに厳しい。測定 3 は未実施。【根拠】`docs/phase2-mlx-eval.md` の測定 1・2・3、チェックリスト「第2段階」の Qwen3-4B 項目

#### W8: 要点・整形（LLM 側）の品質は実機で未確認
- 要点は 3 見出し固定で、見出しが欠けた出力は捨てて前回の要点を保持する（`MeetingNotesPolicy.isComplete`）。捨てたあとの再試行は自動で行われず、次の閾値を待つ。【根拠】`MeetingSession.finishUpdate`、`JournalPrompts.meetingNotesSystem`
- 要点の品質（3 見出しを 1.5B が守るか）、要約本文の品質は、どちらも実機で未確認。【根拠】チェックリスト「会議モード」「Phase 2」節、ADR-024
- 要点のモデルには用語辞書の語彙が渡っていない。文字起こしの誤りは辞書で直る範囲しか直らず、要点がその誤りをそのまま書き写す。【推測】

#### 補足（文字起こしの外側）
- 「金庫」の前提と ADR-040（Claude 選択時は日誌・会議の文字起こしを system メッセージで Anthropic へ送る）の関係は、現行文書では「Claude 選択時のみ・画面で表示」として整理されている。この検討書では変更を提案しない。ただし、文字起こし改善のために Claude 経路を使う案は、前提と衝突するので採らない（4 章）。

## 2. 改善候補リスト

各候補の「測り方」で言う「既存基盤」は、自動チェック（ADR-044）、`cer.journal` ログ行、`tools/cer.py` を指す。

### 候補 1: 実声ベースラインの実施（コード変更なし）
- **狙い**: W1 を解消する。所有者の不満が今どの程度残っているかを、初めて数字にする。
- **根拠**: ベースライン文書「記録表（実声）」が空。チェックリストの実声の未検証 3 項目。ADR-044「実声のベースラインは引き続き正」。
- **期待効果**: 改善の優先順位を、合成音声ではなく実使用の誤り分布で決められるようになる。日誌（30cm）と会議（1m）を比べれば、W5（距離・セッションのモード）が効いているかも切り分けられる。
- **実装の当たり**: 不要。既存の手動読み上げチェック（検証画面）と、ベースライン文書の実声手順をそのまま実施する。辞書 ON/OFF の両方を記録する（OFF は検証画面の辞書スイッチ）。
- **工数感**: 小（所有者の実機作業 30〜60 分）
- **リスク**: 読み手の読み方のぶれ。各条件 2 回ずつ読んで平均する、と手順に注記すると良い。
- **効果の測り方**: 既存基盤（手動チェック = 無印のログ行、`tools/cer.py` での照合）でそのまま測れる。

### 候補 2: 検証文の拡張（実験系列 E: 未見の文と過剰補正の罠）
- **狙い**: W2 を解消する。辞書を作るときに見ていない文での汎化と、過剰補正（誤発動）を測れるようにする。あわせて、文字数を増やして CER の見分ける力を上げる。
- **根拠**: term-accuracy 設計書「評価プロトコル」の E1〜E3 案がまだない。`TermCorrector` の 4 ペアは C から作られている。「企画を超え」系の誤発動の懸念（W2）。
- **期待効果**: 今の C 0.00% が「C だけで成り立つ点数」なのか、本当の改善なのかが分かる。今後辞書が増えたときの退行検知の柱になる。
- **実装の当たり**:
  - `Packages/PocketAgentCore/Sources/PocketAgentCore/TranscriptionScorer.swift` の `TranscriptionCheckPassage` は A〜C の物差しなので触らない。実験用に別の列挙（例: `ExperimentPassage` E1〜E5）を作る。
  - E1・E2: 対象 4 語を別の文脈で使う未見の文
  - E3: 辞書の誤り語を正当な意味で使う罠の文（「前回の企画を超える」「企画外の出し物」など）
  - E4: 用語を含まない長めの日常文（約 300 字、見分ける力の確保）
  - E5: 人名・地名・カタカナ語が多い文
  - 音声は ADR-044 と同じ手順（VOICEVOX、base64 同梱、`App/PocketAgent/Speech/CheckAudio/`）で作る。可能なら話者を 2 種類以上にする。
  - 自動チェックの画面（`TranscriptionAutoChecker`・`TranscriptionExperiment`）に E 系列の実行を足す。ログ行は `cer.journal passage=E1 … src=synth` の形で、A〜C の系列と混ぜない。
  - VOICEVOX での合成は開発 PC 側の作業（AGENTS.md: Windows 環境）。
- **工数感**: 中（文の作成と合成は小、アプリへの組み込みと TDD で中）
- **リスク**:
  - 文を作る人が辞書を知っていると、また「答えを見て作る」形になる。E 系列は辞書を変える前に凍結し、辞書の変更後は「E で発動した件数」を見るだけにする運用ルールが必要。
  - アプリの容量は 1 文あたり数百 KB 増える（16kHz モノラル、base64）。【推測】
- **効果の測り方**: 既存基盤を拡張すれば測れる（新しい系列として記録）。罠の文は「辞書の発動数 = 0」が合格条件。

### 候補 3: 端末内の誤り収集ループ（ユーザー辞書）
- **狙い**: W3 を解消する。所有者が文字起こしを直した結果から、端末の中だけで辞書の候補を作る。所有者が承認したものだけをユーザー辞書として確定テキストに適用する。
- **根拠**: 辞書は固定（`TermCorrector.rules`）。ADR-026 で本文は外に出せないので、開発側での収集は原理的にできない。金庫の前提では、この「端末内で育てる」形しかない。
- **期待効果**: 所有者の実際の分野の繰り返し起きる誤り（人名・社内略語など）が、2 回目以降は直る。【推測】実使用の不満に一番直接効く手段。ただし効くのは「同じ誤りが繰り返し起きる」語だけ。
- **実装の当たり**:
  - Core: `TermCorrector` に外から規則を渡せる入口を足す（今は `static let rules` 固定）。既定の規則とユーザー規則を合成する。ユーザー規則は無条件ペアに限るか、「直後の文字列」条件を付けて登録するかは設計で決める。
  - 永続化: SwiftData か Application Support のファイルに保存する。バックアップ対象外・「全データ削除」の対象にする（ADR-026 / 9.3 の流儀）。
  - 収集: 日誌・会議の文字起こしを編集した画面で、置換の差分（短い語単位）を抽出して「この直し方を辞書に覚えますか？」と提案する。提案は承認制（要件 7 章の「承認」の考え方と同じく、勝手に辞書を変えない）。
  - 適用点は既存の `SpeechCapture.correctFinalText` の 1 か所。単言語と二言語の両経路が既にここを通る（ADR-048）。
  - 検証画面に「ユーザー辞書の件数・発動件数」を出す。ログは件数だけ。
- **工数感**: 大（差分抽出の UI と、辞書の編集・削除画面を含む）。最小版（設定画面で誤り→正しい語を手で登録するだけ）なら中。
- **リスク**:
  - 過剰補正。短い語や普通の語の登録で文章が壊れる。最小文字数や、登録時の警告が要る。
  - 辞書が本文由来の機微な語（人名など）を含むので、辞書自体が機微情報になる。端末外へは一切出さない（測定ログ・Issue 送信に入れない）ことを ADR で明記する必要がある。
- **効果の測り方**:
  - 既存基盤では直接は測れない（固定文にユーザー語彙がないため）。
  - 必要なもの: (a) 実使用の「辞書発動件数」と「発動後にユーザーがさらに直した件数」（誤発動の兆候）をログに件数だけ残す、(b) 候補 2 の罠の文での発動 0 の確認、(c) 所有者が自分の語彙で読む私的な実声チェック（候補 4 があれば再現できる）。

### 候補 4: 端末内に閉じた実声の物差し（所有者の録音を端末内だけで保持して再採点）
- **狙い**: W1 の再現性の問題を解く。候補 1 は一度きりの手動測定なので、設定を変えるたびに読み直す必要がある。所有者の実声を端末内だけに保存し、自動チェックと同じ形で何度でも流し直せるようにする。
- **根拠**: ADR-044 は「実音声はリポジトリに入れない」と定めている（端末内保存は禁止していない）。ただし日誌・会議の設計書は「音声ファイルの保存」を非ゴールにしているので、新しい ADR が要る。【根拠】`docs/superpowers/specs/2026-10-19-meeting-mode-design.md`、`2026-10-18-phase2-mlx-journal-design.md` の非ゴール
- **期待効果**: エンジン設定・音声セッションのモード・辞書の変更を、実声で前後比較できる。W5 の検証にも使える（ただし録音時のセッション設定は録音に焼き込まれるので、モード比較そのものは録り直しが要る）。
- **実装の当たり**:
  - 検証画面の手動チェック（`TranscriptionCheck`）に「録音を端末に残す」オプションを足す。
  - `TranscriptionAutoChecker.transcribeSegments` の入力を、同梱 WAV に加えて端末内の録音ファイルにも広げる（今はパッセージから URL を引く作り）。
  - 保存先は Application Support（バックアップ除外）で、「全データ削除」の対象にする。
- **工数感**: 中
- **リスク**: 端末に声の録音が残るのは、金庫の前提では許容範囲（外に出ない）。ただし利用者に明示する必要がある。容量（1 文 10 秒程度なら小さい）。
- **効果の測り方**: 既存の採点と `cer.journal` 行に新しい印（例: `src=voicefile`）を足せば測れる。

### 候補 5: 音声セッションのモードと距離の切り分け（会議の精度）
- **狙い**: W5。会議（約 1m・机置き・ポケット）での認識を改善する。
- **根拠**: `SpeechCapture.activateSession()` の `.measurement` モード、チェックリストの「会議の文字起こし精度が日誌より悪い件」。
- **期待効果**: 【推測】遠くの話者・小さい声で効果が出る可能性がある。逆に音声処理が認識を悪くする可能性もあるので、結果が出るまで分からない。
- **実装の当たり**:
  - `activateSession()` のモード（`.measurement` / `.default` / `.spokenAudio` など）と、入力ノードの音声処理（`setVoiceProcessingEnabled`）を、検証画面のスイッチで切り替えられるようにする。
  - 既定は変えない（実験 1・2 と同じ ON/OFF 比較の作法、ADR-047）。
  - API の挙動は推測で書かず、SDK と実機で確認する（CLAUDE.md）。
- **工数感**: 小〜中
- **リスク**: セッションは日誌と会議で共有している（ADR-034 の参照カウント）ので、片方だけ変えると不整合が起きうる。音声処理を ON にすると入力形式が変わる場合がある。
- **効果の測り方**: 合成音声の自動チェックでは測れない（マイクを通らないため）。候補 1（その場で読む）か、候補 4 を録音時のモードごとに録り直す方法が必要。

### 候補 6: 長時間会議の途中保存と、会議の測定ログ
- **狙い**: W4。強制終了されても文字起こしを失わない。1 時間会議の安定性を数字で見えるようにする。
- **根拠**: `MeetingSession` に途中保存がない。チェックリストの「1 時間連続」「1 時間の二言語会議」「録音中のモデル読み込み」が未検証。
- **期待効果**:
  - 失われる文字起こしが最大でも直近の数十秒になる。
  - 「何分でメモリ警告が出るか」「要点更新に何秒かかるか」が分かり、Qwen3-4B 格上げ（候補 9）の判断材料にもなる。
- **実装の当たり**:
  - `MeetingSession` で、確定セグメントが一定数・一定秒たまるごとに、端末内の下書き（`JournalDraftStore` と同じ流儀で、原子的に書き込み、id を固定）を書く。
  - 起動時に未終了の会議があれば「復元して保存」を出す。
  - 測定ログ: `meeting.stats minutes=… segments=… chars=… availMB=… thermal=… notesSec=… notesFailed=…`（件数と数値だけ、ADR-026）を 5 分ごとと終了時に記録する。
- **工数感**: 中
- **リスク**: 書き込みの頻度と電池のつり合い。本文を含む下書きを端末に置くこと自体は、日誌の下書きと同じ扱いで問題ない。
- **効果の測り方**: 既存の自動チェックでは測れない。CI では下書きの書き込み・復元の単体テストで確かめる。実機では 1 時間会議を 1 回行い、測定ログを読む。

### 候補 7: 二言語経路の自動チェック
- **狙い**: W6。二言語会議の言語判定と、日本語側の CER を再現性のある形で測る。
- **根拠**: ADR-048 で辞書は二言語にも入ったが、実機確認は未実施。二言語ゲート（段階 A）の未検証 4 件。
- **期待効果**: 日英が混ざる会議での判定の誤り率と、辞書の効果を、回帰の物差しとして持てる。
- **実装の当たり**:
  - 同梱の合成音声（日本語 A〜C と、新規の英語 1〜2 文）を、`SpeechCapture` の二言語と同じオプションで作った 2 つの SpeechAnalyzer に流す。候補を `LanguageArbiter` に通し、判定の一致率と日本語側の CER を出す。
  - `TranscriptionAutoChecker` を「レーン複数」に広げるか、別の型を作る。
- **工数感**: 中
- **リスク**: ファイルを一気に流すと、`LanguageArbiter` の時間ベースの保留（1.5 秒）の挙動が実時間と変わる。音声時刻（`audioTimeRange`）を基準に判定させる工夫が要る。【推測】
- **効果の測り方**: 既存基盤を拡張すれば測れる（判定の一致率という新しい指標が要る）。

### 候補 8: 要点の生成と用語の整合（LLM 側）
- **狙い**: W8。
  - (a) 要点プロンプトに、辞書の正しい語（`TermCorrector` の correction と、候補 3 のユーザー辞書）を「表記の参考」として渡し、要点の表記をそろえる。
  - (b) 3 見出しが欠けて捨てた出力について、直後に 1 回だけ再試行する。
- **根拠**: `JournalPrompts.meetingNotesSystem`、`MeetingSession.finishUpdate`（失敗後は次の閾値まで待つ）。
- **期待効果**: 要点が文字起こしの誤字を書き写すことが減る。要点が更新されない時間が減る。
- **実装の当たり**: `Packages/PocketAgentRuntime/Sources/PocketAgentRuntime/JournalPrompts.swift`、`MeetingSession.runUpdate` / `finishUpdate`。
- **工数感**: 小〜中
- **リスク**:
  - Apple の文脈予算（約 4096 トークン、会議は 1500 字）を語彙リストが圧迫する。
  - 語彙リストを渡すと、モデルが発言にない語を書き足す（幻覚）可能性がある。
- **効果の測り方**:
  - 既存基盤では測れない（CER は文字起こしの指標）。
  - 必要なもの: 固定の文字起こし入力と期待する要点の項目を持つ要点の評価セット（検証画面の MLX 節に相当）と、「見出し欠落率・誤字の写し率」の数え方。

### 候補 9: ダウンロードモデルの格上げ（Qwen3-4B-Instruct-2507）の測定 3
- **狙い**: 要約・要点・チャットの賢さを上げる（文字起こしの CER には直接効かない）。
- **根拠**: ADR-042、`docs/phase2-mlx-eval.md` 測定 3（未実施）、W7（メモリ余裕の見込みの食い違い）。
- **期待効果**: 【推測】要点の 3 見出しを守る率や日本語の要約品質は上がる。速度は半分程度（ADR-042 の見込み）。
- **実装の当たり**: コードは既にある（`MLXModelRegistry.qwen3_4B`）。実機測定だけでよい。ただし測定項目に「会議の録音中に 4B を読み込んだときのメモリ」を必ず入れる。結果によっては「会議中は 4B を使わない」規則（`JournalModelRule` 側）が必要になる。
- **工数感**: 小（測定）。規則の追加が要れば中。
- **リスク**: メモリ警告によるモデル解放・強制終了。W4 と重なると会議の文字起こしを失う（候補 6 が先にあると安全）。
- **効果の測り方**: 既存の MLX 検証画面と測定ログで、速度・メモリ・見出し形式を測れる。要点の品質には候補 8 の評価セットが要る。

### 候補 10: 短文経路での `DictationTranscriber`（用語ヒントあり）の比較
- **狙い**: 日誌の短い音声入力に限って、用語ヒント（contextual strings）を使える認識器を試す。
- **根拠**: term-accuracy 設計書の「前提」「両方とも不採用の場合」（用語ヒントがあるのは `DictationTranscriber` だけ、と記載）。
- **期待効果**: 【推測】辞書（事後の置換）より自然に用語が出る。ただし長文向けの `SpeechTranscriber` より基礎精度が低い可能性がある。
- **実装の当たり**:
  - `TranscriptionAutoChecker` の認識器を差し替えられる形にして、A〜C と E で比べる。
  - API の存在と使い方は、採用する SDK の宣言で必ず確認する（CLAUDE.md「SDK の使用例を推測で書かず」）。この文書は API の形を確認していない。
- **工数感**: 中
- **リスク**: 経路が 2 本になって保守が増える。会議（長文）には使えない。
- **効果の測り方**: 既存の自動チェックに認識器のスイッチを足せば測れる（実験 1・2 と同じ ON/OFF 比較）。

### 候補 11: 端末内の別エンジン（Whisper 系など）との比較
- **狙い**: Apple の認識器そのものの限界を超える。
- **根拠**: ベースライン文書「次の段階」（Whisper 系・SenseVoice 系との比較表を想定）。
- **期待効果**: 【推測】日本語の専門用語や遠い話者で、Apple の認識器を上回る可能性はある。ただし速度・電池・モデル容量（数百 MB〜1 GB 超）と引き換えになる。
- **実装の当たり**: 新しい依存（Core ML や MLX の音声モデル）、モデルのダウンロード経路（ADR-023 の方針を流用）、`TranscriptSource` に合う新しい実装。
- **工数感**: 大
- **リスク**:
  - メモリ（LLM と同時に載せる）、ライセンス、依存の pin の管理（ADR-036 の経緯）。
  - バックグラウンド・ロック中に GPU や Neural Engine の推論ができるか分からない（ADR-033 では、端末内生成はバックグラウンドで使えない前提）。
- **効果の測り方**: 自動チェックの認識器を差し替えれば測れる。ただし実声（候補 1・4）がないと、エンジンを替えるかどうかの判断はできない。

### 候補 12: 話者分離
- **狙い**: 会議の文字起こしを「誰が言ったか」付きにする。
- **根拠**: 会議・日誌・二言語の各設計書が非ゴールにしている（`2026-10-19-meeting-mode-design.md` ほか）。ADR-035 の根拠「話者のタップ切替はユーザーが不可とした」。
- **期待効果**: 要点の「担当」欄の精度が上がる。
- **実装の当たり**: 【推測】SpeechAnalyzer に話者分離の公開機能は見当たらない（この文書では未確認）。サードパーティの端末内モデルが必要になる。
- **工数感**: 大
- **リスク**: メモリ・電池、ロック中に動くかどうか、精度。
- **効果の測り方**: 既存基盤では測れない。複数話者の評価音声と、話者誤り率の採点器が要る。

## 3. 優先順位（推奨する上位 3 件）

### 1 位: 候補 1 — 実声ベースラインの実施（＋手順に「各条件 2 回」を追加）
- コード変更なしで、最大の弱み W1 を直接解消できる唯一の手段。
- これがないと、残りすべての候補の効果を実使用の言葉で語れない。会議（1m）と日誌（30cm）の差が大きければ、次の一手が候補 5（セッションのモード）や候補 4 に変わる。誤りが人名・社内語に偏っていれば候補 3 が最優先になる。どれが当たるかはこの測定で決まる。
- 工数が最小で、所有者の実機作業だけで済む。

### 2 位: 候補 2 — 検証文の拡張（実験系列 E、罠の文を含む）
- 公式値の C 0.00% は、辞書の作り方から見て汎化の証拠にならない（W2）。今のまま辞書を増やすと（候補 3）、過剰補正を検知する物差しがないまま実経路の確定テキストを書き換え続けることになる。
- 「企画を超える」の誤発動のような具体的な懸念を、先に固定の回帰テストとして押さえておく必要がある。
- 既存の自動チェック基盤の延長で作れて、合成音声の手順（ADR-044）も確立済み。

### 3 位: 候補 3 — 端末内の誤り収集ループ（まず最小版: 手動登録のユーザー辞書）
- 金庫の前提（本文は外に出さない、ADR-026）のもとで、所有者固有の誤りを継続的に直せる唯一の経路。所有者の不満に一番直接効く。
- 1 位で実際の誤りの傾向が分かり、2 位で過剰補正の物差しができてから入れれば、安全に育てられる。この順番にする理由はそこにある。
- 最小版（設定画面での手動登録＋既存の適用点 `correctFinalText` の 1 か所への合成）なら中規模で始められる。編集差分からの自動提案は、その後に足す。

### 次点
- 候補 6（会議の途中保存と測定ログ）は、精度ではなく「失わない」ための施策なので 4 位に置いた。ただし、所有者が長い会議の途中終了で文字起こしを失ったことが一度でもあれば、1 位と入れ替えるべき（失った会議の精度は 100% 誤りと同じ）。
- 候補 4（端末内の実声の物差し）は、候補 1 を 2 回以上繰り返す必要が出た時点で着手する。

## 4. 今はやらない方がいいこと

### 前提（金庫・オフライン）と衝突するもの
- **クラウドの音声認識（クラウドの Whisper API など）や、Claude による文字起こしの整形・補正**: 会話本文を端末外へ出すことになり、存在理由と真っ向から衝突する。Claude 経路が残っていても、文字起こし改善の手段には使わない。
- **誤り例・辞書・文字起こし本文の開発側での収集**（測定ログ・GitHub Issue 送信・TestFlight フィードバックへの添付）: ADR-026 と金庫の前提に反する。開発側に届けてよいのは件数と CER だけ。ユーザー辞書（候補 3）も同じ扱いにする。
- **実声の録音をリポジトリや CI に置くこと**: ADR-044・ベースライン文書の前提で禁止。候補 4 は端末内だけで完結させる。
- **クラウドからの辞書・用語リストの自動配信**: 中身は機微でなくても、通信が必要な処理を増やすと「オフラインで完結」の説明が崩れる。辞書の既定値はアプリ同梱で配る。

### 時期尚早なもの
- **エンジンの差し替え（候補 11）**: 実声ベースラインがない今、比較しても判断できない。メモリの余裕（W7）と、ロック中に推論できるかどうかも未確認。
- **Qwen3-4B の既定への昇格**: 測定 3 が未実施で、ADR-042 のメモリ余裕の見込みが記録上の数値と食い違っている（W7）。測定 3 と候補 6 の測定ログが出るまでは「候補のまま」にする。
- **話者分離（候補 12）**: 設計書で非ゴールにされており、公開 API がない。精度の土台（単一話者の CER）が固まる前に手を出す段階ではない。
- **LLM による文字起こしの全文書き直し（自由な整文）**: 1.5B 級のモデルでは内容の捏造や欠落の危険が大きい。採点の物差し（CER）とも衝突し、改善か改悪かを測りにくい。やるとしても候補 8 のように「表記の参考を渡す」程度の制約付きにとどめる。
- **固定文 A〜C の変更・差し替え**: 系列の連続性が壊れる（ADR-046 の系列の扱い）。増やすなら E 系列として別枠にする。
- **実験 1（代替候補）の再開**: 実機で候補ヒット 0 件で不発だった（ADR-047）。エンジンが変わるか、候補リストが空かどうかを判別する手段ができるまでは保留でよい（チェックリスト「実験1」の未検証項目）。
